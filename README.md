# Разделение затрат (cost_sharing)

Веб-сервис для учёта общих расходов и честного распределения долгов внутри
компании людей: участники фиксируют покупки по событиям с коэффициентами
участия, а сервис считает итоговый отчёт «кто, кому и сколько должен» в виде
треугольной матрицы долгов.

## Возможности

* страницы сайта: главная (кнопки добавления человека / события / покупки,
  просмотра покупок и ссылка на отчёт), формы добавления, страница
  «Просмотр покупок» с карточкой каждой покупки, страница отчёта о должниках
  с выгрузкой в **XLS** и **PDF**;
* JSON API: добавление человека, события, покупки с разделением по должникам,
  карточка покупки, получение отчёта по событию;
* отчёт «кто-кому-сколько» строится **одним SQL-запросом** к SQLite в виде
  квадратной матрицы с нулями на главной диагонали;
* админка Django для просмотра и правки всех таблиц (`/admin/`).

## Модель данных (SQLite + ORM)

Схема состоит из четырёх таблиц, имена заданы точно (`Meta.db_table`):

| Таблица | Поля |
|---|---|
| `people` | `id`, `full_name` (ФИО в свободной форме), `nickname` (краткий никнейм), `is_admin` (флаг администратора сайта) |
| `events` | `id`, `date` (дата события), `description` (краткое описание) |
| `purchases` | `id`, `description` (краткое описание покупки), `event_id` (FK → events), `person_id` (FK → people, кто совершил покупку), `amount` (сумма, см. замечание ниже) |
| `debtors` | `id`, `person_id` (FK → people), `purchase_id` (FK → purchases), `share` (коэффициент участия 0 < x <= 1, по умолчанию 1) |

Связи соответствуют требованиям: одно событие — много покупок; каждая покупка
относится ровно к одному событию и оплачена ровно одним человеком; запись
`debtors` связывает человека с покупкой и показывает его долю потребления.

**Про поле `amount`.** В списке обязательных полей таблицы `purchases` суммы
не было, но без неё отчёт «кто-кому-сколько» невозможно посчитать в деньгах,
поэтому `amount` добавлено осознанно как дополнение к обязательному минимуму
(денежные суммы по-прежнему нигде не дублируются).

Ограничения целостности: CHECK `0 < share <= 1` на уровне БД, валидатор на
уровне модели, уникальность пары (человек, покупка) в `debtors`, запрет
удаления человека, у которого есть покупки или записи о потреблении
(`PROTECT`), каскадное удаление покупок вместе с событием.

## Правила расчёта долгов

Долг по отдельной покупке:

```
доля_должника            = share / SUM(share всех должников покупки)
долг_должника_покупателю = доля_должника * amount покупки
```

Коэффициенты участия **нормализуются** перед расчётом: сумма долей всех
участников покупки приводится к 1 (доли 1 + 1 + 1 + 0,5 превращаются в
0,2857 + 0,2857 + 0,2857 + 0,1429). Нормализация применяется везде: в
SQL-отчёте (`SUM(share) OVER (PARTITION BY purchase_id)`), в карточке
покупки (`/purchases/<id>/`, `core/reports.py::split_purchase`) и в API
(`GET /api/purchases/<id>/`). Копейки округления добавляются к наибольшей
доле, поэтому сумма денег по участникам совпадает с суммой покупки.

* человек с `share = 1` платит как все; `share = 0.5` — вдвое меньше тех,
  кто съел полную порцию;
* покупатель, потребивший свою долю, сам себе не должен (доля «сам себе»
  исключается);
* покупатель, которого нет в `debtors` (платил, но не потреблял), только
  получает деньги;
* долги каждой пары участников **взаимно зачтены** (нетто-расчёт): если Аня
  должна Боре 150, а Боря Ане 22.5, в отчёте останется «Боря должен Ане 127.5».

## SQL-запрос треугольной матрицы

Отчёт строится одним запросом (`core/reports.py`, `MATRIX_SQL`) — участники
берутся из связи `debtors -> purchases -> events` плюс плательщики из
`purchases -> events`, матрица формируется перекрестным соединением:

```sql
WITH ev AS (          -- покупки выбранного события
    SELECT p.id, p.person_id AS buyer_id, p.amount
    FROM purchases p
    WHERE p.event_id = %s
),
parts AS (            -- должники и суммарный коэффициент каждой покупки
    SELECT d.purchase_id, d.person_id, d.share,
           SUM(d.share) OVER (PARTITION BY d.purchase_id) AS total_share
    FROM debtors d
    WHERE d.purchase_id IN (SELECT id FROM ev)
),
direct AS (           -- направленные долги «должник -> плательщик»
    SELECT parts.person_id AS from_id, ev.buyer_id AS to_id,
           SUM(parts.share * ev.amount / parts.total_share) AS value
    FROM parts
    JOIN ev ON ev.id = parts.purchase_id
    WHERE parts.person_id <> ev.buyer_id
    GROUP BY parts.person_id, ev.buyer_id
),
participants AS (     -- участники события, упорядоченные по алфавиту
    SELECT pp.id, pp.full_name, pp.nickname,
           ROW_NUMBER() OVER (ORDER BY pp.full_name COLLATE NOCASE, pp.id) AS pos
    FROM people pp
    WHERE pp.id IN (SELECT buyer_id FROM ev
                    UNION SELECT person_id FROM parts)
)
SELECT a.pos AS row_pos, b.pos AS col_pos,
       ROUND(COALESCE(d1.value, 0) - COALESCE(d2.value, 0), 2) AS debt
FROM participants a
CROSS JOIN participants b
LEFT JOIN direct d1 ON d1.from_id = a.id AND d1.to_id = b.id
LEFT JOIN direct d2 ON d2.from_id = b.id AND d2.to_id = a.id
ORDER BY a.pos, b.pos
```

Пояснение «треугольности»: на главной диагонали — нули (человек сам себе не
должен); выше главной диагонали — сумма долга человека A (номер строки)
человеку Б (номер столбец); ниже диагонали — те же значения зеркально со
знаком минус, поэтому вся картина долгов читается по одному верхнему
треугольнику (матрица антисимметрична). Запрос можно посмотреть прямо на
странице отчёта (раскрывающийся блок «Показать SQL-запрос»).

Порядок людей в матрице — алфавитный (стабильно и удобно для чтения).

## Страницы сайта

| URL | Назначение |
|---|---|
| `/` | главная: кнопки добавления человека / события / покупки, ссылка на отчёт, счётчики |
| `/people/add/` | форма добавления человека |
| `/events/add/` | форма добавления события |
| `/purchases/add/` | форма добавления покупки: событие, плательщик, описание, сумма + таблица «кто участвует и с каким коэффициентом» |
| `/purchases/` | просмотр покупок: список покупок по событиям — выберите покупку для просмотра |
| `/purchases/<id>/` | карточка покупки: кто купил, сумма, кто участвует с нормализованной долей (сумма долей = 1) и сколько это в рублях |
| `/report/` | отчёт о должниках по выбранному событию: матрица долгов, кнопки «Выгрузить XLS» и «Выгрузить PDF» |
| `/report/<id>/export/xlsx/`, `/report/<id>/export/pdf/` | файлы выгрузок |

## JSON API

| Метод и URL | Назначение |
|---|---|
| `POST /api/people/` | добавление человека |
| `POST /api/events/` | добавление события |
| `POST /api/purchases/` | добавление покупки с разделением по должникам |
| `GET /api/purchases/<id>/` | карточка покупки: покупатель, сумма, участники — исходная доля `share`, нормализованная `share_normalized` (сумма = 1) и сумма на каждого `share_amount` |
| `GET /api/events/<id>/report/` | отчёт о должниках события (матрица) |
| `GET /api/people/`, `/api/events/`, `/api/purchases/` | списки (для удобства) |

Примеры (сервер запущен локально):

```bash
# человек
curl -s -X POST http://127.0.0.1:8000/api/people/ \
  -H 'Content-Type: application/json' \
  -d '{"full_name": "Иванов Иван Иванович", "nickname": "Иван", "is_admin": false}'

# событие
curl -s -X POST http://127.0.0.1:8000/api/events/ \
  -H 'Content-Type: application/json' \
  -d '{"date": "2026-11-08", "description": "Поездка на дачу"}'

# покупка с разделением по должникам (запятая вместо точки в сумме допустима)
curl -s -X POST http://127.0.0.1:8000/api/purchases/ \
  -H 'Content-Type: application/json' \
  -d '{"event": 1, "person": 1, "description": "Продукты для шашлыка",
       "amount": "3250.00",
       "debtors": [{"person": 1, "share": 1}, {"person": 2, "share": 1},
                   {"person": 3, "share": 1}, {"person": 4, "share": 0.5}]}'

# карточка покупки: кто купил, сумма, кто участвует и с какой долей
curl -s http://127.0.0.1:8000/api/purchases/1/

# отчёт о должниках события
curl -s http://127.0.0.1:8000/api/events/1/report/
```

Ответ отчёта: `participants` (порядок = порядок строк/столбцов матрицы),
`matrix` (числа с округлением до копеек, нули на диагонали), `totals`
(нетто-баланс каждого участника: положительный — должен в целом,
отрицательный — ему должны в целом).

## Выгрузки

* **PDF** — reportlab, шрифт DejaVu Sans (кириллица), та же матрица с легендой.

## Замечания

* `DEBUG = True` и `SECRET_KEY` в `settings.py` — для разработки; для боевого
  окружения выключите DEBUG, задайте свой `SECRET_KEY` и `ALLOWED_HOSTS`.
* Путь к базе переопределяется переменной окружения `COST_SHARING_DB_PATH`.
* Экспорт «XLS» выполняется в формате `.xlsx` (актуальный формат файлов
  Excel; устаревший бинарный `.xls` не поддерживается современными
  библиотеками и Excel).
